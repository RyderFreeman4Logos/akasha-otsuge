## 1. 优先级与证据使用

用户在本规格之后的明确决定优先；其次是本规格中对应需求、接口和验收条件。若需求与技术细节出现冲突，先记录具体差异并修正文档，不能默默选择更容易的实现。旧讨论、旧仓库README、模型生成建议和外部研究仅提供背景。

实现前核查实际稳定版本及capability；依赖固定到可复现版本，并将commit、版本、文档URL和测试结果写入仓库ADR。避免将文档发布版本、Rust SDK crate版本、CLI版本和Docker镜像tag混用。

## 3. 决策记录

| 编号 | 状态 | 决定 | 理由或约束 |
| --- | --- | --- | --- |
| D-01 | 确认 | consult允许短可选hint，仍支持无参数；上下文绑定由程序取得。 | 取代早期“强制零参数”设计；减少猜错方向，避免主Agent转述大包上下文。 |
| D-02 | 确认 | 四种CLI各自可独立使用，Caller与Runner分别抽象，可任意路由。 | 不固定Claude+Codex组合；不要求额外模型API才能基本使用。 |
| D-03 | 确认 | Rust核心、CLI和私有本地IPC；MCP不是MVP依赖。 | 保留薄的宿主语言适配，不用一个通用shell入口假装已经完成四种集成。 |
| D-04 | 确认 | 本地provider单请求与Runner单次执行各默认1700秒；workflow auto按预算推导。 | 两种1700计时边界不同；隐藏短时限不可接受，显式用户限制可覆盖。 |
| D-05 | 确认 | 尽可能热重载；完整验证后原子生效。 | 任务固定可复现配置，权限/资源撤销与通知投递路由使用明确live控制。 |
| D-06 | 选型门槛待执行 | 先实验Helix embedded；不达标再评估SurrealKV+LanceDB；最终仅一个backend。 | 没有预先宣布性能通过，也不因拒绝SQLite就假定任何新引擎天然合适。 |
| D-07 | 确认 | 原文、不可变修订、持久提交和实际RecallReceipt独立保留。 | 数据库短期snapshot不能代替产品历史；后来修订不改写过去实际返回。 |
| D-08 | 确认 | 外部Agent提出有scope和expected\_revision的修订，内核校验与提交。 | 资源、模型强弱、人工review投入由用户配置；自动批准不伪装成人类确认。 |
| D-09 | 确认 | 执行反馈只提供调查证据；通知采用统一接口和持久outbox。 | 出现坏结果不自动证明某条记忆有因果责任；可高优review或有依据自动修订。 |
| D-10 | 本规格的MVP边界 | Linux安装交付优先；默认单daemon写入；原生多OS安装器、daemonless模式、远程多用户服务后置。 | 控制第一版开发面；不得把本范围选择误称为用户原话。 |
| D-11 | 本规格提出的验收门槛 | 512MiB默认目标与2GiB档、50GB/100客户端、60任务质量集及近1700秒实测。 | 这些是可验收工程目标，尚未执行；精确定义以资源页和验收页为准。 |
| D-12 | 确认 | 先创建28个真实GitHub Issues，再按依赖逐项实现。 | Notion为开发规格与Issue正文来源；本次不创建新仓库、不假报实现进度。 |

## 4. 尚须实施验证的事实

- 各宿主真实稳定版能提供哪些事件、分支身份、压缩前原文及长任务恢复机制。
- 本地CLI内部与provider的有效deadline是否可控；每种local profile据实报告验证状态。
- 候选数据库能否满足实际RSS、SSD构建、索引积压、历史分页、重启恢复与许可证条件。
- 100客户端持续做事时的吞吐和尾延迟，后台索引与长模型等待是否挤占交互路径。
- 可选hint、渐进披露和后台委派在冻结任务集上的质量、主上下文节省与外部成本。

这些验证已有对应Issue，不要求先有答案才创建Issue，也不能没有答案就关闭这些Issue。

## 5. 变更记录模板

每次实质变更记录：日期、规格版本、提出者/证据、原要求、新要求或实现策略、理由、受影响REQ与Issue、迁移影响、需重跑的具体测试、批准或决定的来源。

纯实现策略变化在保持契约时可由开发Agent决定。减少用户明确要求或降低产品完成门槛需要清楚标记为范围变化，并取得相应用户决定；不能把测试失败直接改成新的通过标准。

## 6. v0.1 本轮变化

- 接受简短可选hint，不再强制无参数。
- 四工具Caller/Runner分别接入；单独安装一种也可完成基础流程。
- 配置热重载和本地1700秒默认成为正式需求。
- 版本历史、实际返回、外部纠正、运行反馈、通知接口与资源预算拆成可实施契约。
- 以12个专题页面与28个必需Issue组织MVP；每项有依赖和验收，先建完整Issues再实施。
