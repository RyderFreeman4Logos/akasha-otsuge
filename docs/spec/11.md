## 1. 建立与执行规则

先阅读 [10｜开发 Agent 执行手册](https://app.notion.com/p/40117b41f58c814ba2c8c2cbef66219c)，创建完整Issue集合及真实链接映射，然后按依赖顺序逐项实施。最终门槛见 [09｜验收矩阵、质量门槛与 MVP 完成标准](https://app.notion.com/p/40117b41f58c8129bf52e98ae1bf7016)。默认数字顺序就是有效拓扑顺序；默认一次只处理一个主Issue。内部可以委派研究或审查，但不得以“并行开发”为由跳过尚未完成的依赖。

所有Issue同属MVP milestone。阶段只是阅读与检查分组，不是另外一组重复Issue。新发现可以拆分或增加必要缺陷Issue，但必须保留原有验收责任，并将阻塞接入最终验收。

## 5. Issue 关闭门槛

- 依赖已满足；实现与规格一致，无必需占位分支。
- 本Issue要求的真实测试有结果、环境版本和可复现步骤；需要真实CLI、数据或长测的地方没有仅用mock替代。
- 提交/PR已符合仓库合并要求；验收产物与实际commit对应。
- 已记录必需限制及新增缺陷，阻塞最终MVP的问题已挂入计划。
- 没有把用户要求改为“未来支持”后关闭Issue。

## 6. 计划内部一致性

本清单的24项需求全部被至少一个MVP-001～027实质工作项覆盖；所有显式依赖均指向前置项，最终MVP-028依赖前27项。创建真实GitHub Issues后必须重新验证映射、链接和新增依赖。

早期配置/存储实验使用独立测试消费者或harness；后续生产集成负责再次验证，不形成对未来Issue的循环依赖。长超时的provider直接路径在MVP-009完成，真实CLI本地路径在宿主接入及MVP-016/027补齐。
