## Issue 正文

\*\*覆盖需求：\*\*REQ-18、REQ-19、REQ-20、REQ-21、REQ-23。

\*\*目标：\*\*用可复现测量选择一种能承受实际数据规模的正式持久方案。

\*\*范围：\*\*先验证 HelixDB embedded，关键门槛失败才验证 SurrealKV + LanceDB 组合；使用独立 Rust spike harness 模拟 100 个存储客户端，不依赖 MVP-008 的生产 CLI/daemon；验证磁盘检索、范围过滤、版本历史、批量写入、撤回过滤、原文读取、并发和恢复。记录采用一个权威 backend 时索引与 blob 如何组织。先固定 benchmark、资源预算和评价标准，再测量、写 ADR、选择一种方案。

\*\*非目标：\*\*不实现两个完整产品 backend；不默认 SQLite；不凭小数据演示或推算宣称 50 GB/100 客户端已通过。

\*\*依赖：\*\*MVP-001、MVP-002。

\*\*验收测试：\*\*按存储与资源子页，使用逐步增大至 50GB 的实际数据、100 个 harness 客户端，完成 512MiB/2GiB 档和冷热读写混合测试；MVP-024 再经生产协议复用同一 manifest/oracle 回归；测得内存、延迟分位数、吞吐和索引体积；证明选定方案能提供后续需要的原子提交/恢复语义；ADR 说明淘汰原因及未验证风险，保留的正式 backend 只有一个。

\*\*完成证据/产物：\*\*ADR、可复现 benchmark 命令、数据 manifest、原始结果、选型结论；临时原型从正式实现路径移除。
