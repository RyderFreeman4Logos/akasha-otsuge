## 1. 目标与边界

使用 Rust 实现一个由当前用户拥有的本地 daemon。Claude Code、Codex、Hermes Agent 和 pi 可以单独或任意组合，通过 CLI 调用同一服务；数据库和检索实现不得依赖某一种 agent，也不得要求安装 MCP。

MVP 必须承载几十 GB 的真实可检索内容，支持 100 个客户端连接和有界的并发工作，提供持久 receipt、不可变修订、纠错撤回、历史状态查询以及可恢复的索引任务。内存不足时允许查询变慢、任务排队或返回明确的可重试错误，不允许无限扩张内存或悄悄丢弃已经确认持久化的数据。

MVP 只交付一种数据库 backend。内部可以保留满足测试所需的最小存储接口，但不建设通用插件系统，不在正式产品中同时维护 Helix、SurrealKV、SQLite 等多套实现。

### 术语

| 术语 | 本规格中的含义 |
| --- | --- |
| 权威数据 | 原文事件、不可变 memory revision、提交记录、receipt、当前 head、持久任务；可据此重建派生数据 |
| 派生数据 | embedding、全文/向量索引、查询缓存、可重建摘要和统计 |
| `commit_seq` | daemon 分配并随权威事务持久化的单调提交序号；不是模型生成的时间戳 |
| `at` / `as_of` | 查询系统在某个已提交序号时知道并采用了什么；不表示现实世界某事实的发生时间 |
| `CommitReceipt` | 写操作持久回执；区分排队、权威提交和索引可见 |
| `RecallReceipt` | 实际准备/返回给调用方的内容、所选 revision、调用 binding、配置与索引版本；不能用写入回执代替 |
| `generation` | 一次索引定义、embedding 模型/维度及构建结果的身份；不得在不同 generation 间混用向量 |
| `head` | 某个逻辑记忆当前生效的 revision 引用；旧 revision 仍保留 |

## 2. ADR-001：先验证 HelixDB embedded，失败才进入组合备选

### 决定

优先验证 HelixDB embedded，初始源码基线为仓库发布 tag `v3.5.1`。该 tag 内 Rust SDK 的包版本为 `3.0.0`；两种版本号不能混写。spike 开始时须记录实际依赖版本、Git commit、Cargo.lock 和构建方式，不得只写 `latest`。

若 Helix 未通过本页规定的关键门槛，允许进入一次明确的备选验证：**SurrealKV 1.0.0 作为权威数据存储，LanceDB stable 0.40 系列作为派生检索存储**。备选必须使用可实际调用的 Rust API，并验证所需的预算、spill、索引和历史接口；不能因为 Python 文档展示了某个参数，就假定 Rust SDK 也暴露了它。

spike 完成后，更新 ADR，写明通过的唯一 backend、精确版本、已测限制以及放弃另一候选的原因。未入选的 prototype 不进入正式运行路径。若两条路线均未达到必要契约，阻断后续实现，提交具体失败证据及待决策项；不得自动扩大为数据库大选或带着未满足的核心条件继续开发。

### 选择依据

Helix 在一个引擎内提供图、向量和 BM25，Rust embedded 不需要 HTTP 服务。已发布源码中存在有限缓存、向量缓存缺失时回读存储、索引构建预算和 pending work 限流机制，适合先验证一套较少自建协调代码的方案。它采用 Apache-2.0。

SurrealKV 1.0.0 提供持久版本化 KV，包括 `get_at`、`history` 和 retention；LanceDB 负责派生检索。这个组合必须由本项目负责 outbox、索引水位、模型 generation、恢复与失效过滤，复杂度较高。SurrealKV 1.0 是 2026-10-13 发布的新底层实现，不能按旧 0.21 系列的使用历史推定其成熟度。SurrealKV 与 LanceDB 的许可证及所采用依赖版本须在依赖清单中保留。

SurrealDB 当前主引擎采用 BSL 1.1，和 Apache-2.0 的 SurrealKV 不同。本 MVP 不把它列为自动 fallback，也不要求实现 Agent 无限制横向比较其它数据库。

### 已知风险必须进入验证

| 风险 | 对实现的约束 |
| --- | --- |
| Helix 的 cache budget 不是整个进程 RSS 上限 | 必须测冷启动、并发请求、恢复和构建；不得把几个 cache 数字相加后宣称满足总内存目标 |
| 已发布 Helix 的 pending work 默认约 1 GB/index，strong text 分析默认 512 MiB | 不使用这些默认值作为低内存产品配置；逐项设置，并做 daemon 级总准入控制 |
| strong vector 的预算检查在读取 stored queue 之后 | 必须测试已有大 backlog 重启及降低 profile；不能仅限制后续解码阶段 |
| vector build cache 默认有独立预算，无法识别内存上限时可能取 256 MiB | 显式设置构建预算和并发，不能继承宿主机内存推断作为产品承诺 |
| Helix 事务 snapshot 不等于公开的任意持久 `AS OF` API | MVP 的历史状态由本项目的 immutable revision/历史索引契约保证，不能用短期 MVCC snapshot 冒充 |
| Helix v3.5.1 没有 text split blob 回收协议 | 重建会增加磁盘占用；MVP 要可测量、可限制重建并检查可用空间，不假称已有安全 GC |
| SurrealKV 的 native history 不是历史 ANN/BM25 | 备选也必须实现显式的历史状态和索引 generation 契约 |
| SurrealKV `memory.rs` 注释不能证明全局预算已经完整接入 | 以实际调用链和受限资源实测为准，不以注释中的“防 OOM”通过验收 |

## 3. 早期 storage spike：必须交付什么

spike 是一段可丢弃的最小存储程序和可重复测试，不是先把完整产品写完。MVP-003 使用独立 Rust harness 与最小调用协议模拟 100 个并发客户端，不依赖尚未实现的生产 CLI/daemon、四宿主或调研 workflow。MVP-024 才通过正式 CLI/daemon 对同一数据 manifest 和正确性 oracle 完成产品路径回归。必须调用候选引擎的真实 Rust API，包含权威事务、revision/head/receipt、小型持久任务队列和检索路径。

必须交付：

1. 一个精确版本的可重现构建及依赖锁文件。
2. 最小 schema/键布局、事务边界、持久确认边界和原文布局说明。
3. 本页与下一子页规定的测试命令、数据 manifest、原始测量结果和通过/失败结论。
4. 512 MiB 与 2 GiB daemon profile 的实际参数；包括 cache、未 flush 数据、pending work、查询工作区和构建预算。
5. 最小历史读接口：按 memory ID 和 `commit_seq` 读旧状态，以及按 scope 分页枚举某时刻有效状态。
6. 崩溃、纠错、索引落后、重启和低内存恢复的结果；不能只展示开库、写入和一次成功检索。

### 必须通过的门槛

| 门槛 | 通过条件 | 失败后的处理 |
| --- | --- | --- |
| 原子提交 | revision、head、receipt 和派生任务同成同败；故障后不存在半个逻辑提交 | 修复 adapter；若底层无法提供可靠原语，退出该候选 |
| 持久确认 | 返回 `committed` 后进程被强制终止，再次打开仍可恢复该提交；不把“已进入内存队列”称为持久提交 | 查明引擎的持久边界；无法通过则退出候选 |
| 历史状态 | 跨重启后能准确恢复多个已知提交点；不从第一条原始事件全量 replay 才能回答一次正常历史查询 | 实现有序历史索引或检查点；仍不能满足资源/规模门槛则退出 |
| 低内存大数据 | 50 GB 验收集在 512 MiB 目标档下可冷开、查询、写入和恢复；峰值符合下一页定义，且无 OOM、无无限内存队列 | 调整真实可用预算入口；必要路径仍无法受限则退出 |
| 100 客户端 | 通过下一页的稳态和突发负载；不是只连上 100 个空闲 socket | 修复准入/事务/背压；不得用拒绝几乎全部请求通过稳态档 |
| 索引正确性 | 纠正后新查询不返回旧生效版本；落后/损坏可察觉、可重建；索引未完成不能被报告为“全量最新” | 不满足时不能接入 agent 自动决策 |
| 重启与降预算 | 存在 backlog、未完成构建和超时任务时，仍能在所选低内存 profile 内恢复，或以明确受限模式启动并流式消化 | 无法低内存恢复的数据布局应在 spike 内修改，不能留到发布后 |
| 磁盘成本 | 已记录原文、权威记录、各索引、旧 generation、临时文件的实际大小；重复重建不会失控填满磁盘 | 加空间预检和重建上限；需要未知私有 API/危险清理才能维持则退出 |

功能小样本可以先跑，但大规模和低内存门槛同样属于早期 spike 的完成条件。相同数据 manifest 和测试套件用于最终 MVP 回归，避免重复构造不同口径的“成功”。

## 4. 权威记录与不可变修订

### 最小逻辑记录

| 记录 | 必须包含的字段或关系 |
| --- | --- |
| `SourceEvent` | `event_id`、来源工具/会话、原始 actor/provenance、scope、source timestamp、接收时间、原文或不可变原文引用、内容校验值、去重身份 |
| `MemoryRevision` | `memory_id`、`revision_id`、`commit_seq`、前序 revision、操作类型、内容、scope、来源证据、origin/adoption、采用的 policy revision |
| `MemoryHead` | `memory_id`、当前 `revision_id`、状态、最新 `commit_seq`；可由 revision 记录重建 |
| `CommitReceipt` | `request_id`、规范化请求 hash、`receipt_id`、提交结果、`commit_seq`、涉及 revision、配置/策略版本、错误或冲突信息 |
| `DerivedJob` | job ID、源 revision、任务类型、目标 generation、状态、重试次数、租约/执行者信息、输出引用、错误 |
| `RecallReceipt` | invocation/run、实际返回 bytes 或不可变 blob、内容 hash、selected revisions、来源引用、read\_seq、index/config generation、覆盖/截断状态和发送阶段 |
| `IndexGeneration` | 类型、模型/维度/距离函数或 tokenizer 版本、构建状态、覆盖范围、应用水位、构建/失败时间 |

origin/adoption 的详细权限遵循权威策略子页；存储层必须保留它们，不能由重新提取或重建索引改写。

### 事务规则

一次逻辑修改在一个权威事务中完成：验证 `expected_revision`，追加不可变 revision，切换 head，写 receipt，追加所需派生任务，推进 `commit_seq`。事务中不运行模型、外部 CLI 或网络请求。

如果原文采用独立不可变 blob，必须先完成 blob 的写入、校验及所需持久化，再提交引用它的权威事务。失败可以产生尚未被引用的 blob，不能产生已确认提交但指向缺失原文的记录。原文具体放库内还是 blob 层，由 spike 选择一次并写入 ADR；MVP 不实现可热切换的多种原文格式。

删除错误记忆使用 retract/supersede 等追加修订。常规纠错和 rollback 不调用会擦掉全部历史的底层 hard delete/replace。真正删除用户数据属于显式的删除操作，须另有范围和派生数据清理契约，不能与纠错混用。

### 并发、纠错与 rollback

- editor 返回的 patch 必须携带它读到的 revision。与当前 head 不符时返回冲突，不能最后写入者覆盖一切。
- 用户明确否定某条已生效记忆后，先提交该条的撤回/失效 revision，再等待更强模型生成替代内容；不能在 1700 秒模型等待期间继续把明确错误项当有效记忆。
- 项目例外只修改所声明 scope，不顺手改成全局偏好。存储必须支持同一概念在不同 scope 中并存。
- rollback 创建补偿修订并检查它要补偿的 head。若中间已发生新修改，返回冲突或产生待重算任务；不覆写 intervening changes。
- 旧 receipt 继续表示“该操作曾经提交成功”。之后被撤回、替代或补偿，不把旧 receipt 改写成从未提交。

## 5. Receipt 与幂等契约

所有写操作接受稳定的 `request_id`。同一个 `request_id` 与相同规范化请求重试时，返回同一个 receipt 和已存在结果；与不同请求内容重用时返回 `idempotency_conflict`。幂等记录不得只留在进程内存。

| 阶段 | 可以向调用方承诺的内容 |
| --- | --- |
| `queued` | 任务请求已进入持久队列；尚不代表记忆修订已经采用或索引完成 |
| `committed` | 对应权威修改已经越过配置要求的持久边界，拥有 `commit_seq`；直接读取和历史状态可见 |
| `indexed` | 指定的派生索引任务/目标 generation 已达到明确可查询的覆盖条件；不得笼统声称所有模型、所有历史索引均完成 |
| `failed` / `rejected` | 没有完成承诺的权威修改；返回结构化原因。若结果不确定，必须先按 request ID 恢复结果，不能猜测未提交 |

`queued` 与 `committed` 是不同操作阶段，也可以对应不同 receipt。例如“采集原文已提交”不等于“模型提取后的记忆已发布”。接口须清楚返回对应对象和阶段。

receipt 应可单独查询，并支持等待某个明确阶段。CLI 超时、退出或连接断开后，daemon 可以继续一个已经开始的提交；重试必须先查询幂等结果。不得因为调用方取消就把已持久提交的数据删除。

索引任务因该 revision 已被更新版本替代而不再需要时，记录 `superseded`，不能把它伪报为“历史向量索引已建立”。

## 6. MVP 必须有的历史查询

必须提供与具体 CLI 命名无关的以下能力：

1. `get(memory_id, at)`：在指定已提交点读取当时生效的 revision 或明确的不存在/撤回状态。
2. `state(scope, at, cursor, limit)`：在固定提交点按 scope 分页返回当时有效状态；下一页仍绑定同一个 `at`。
3. `history(memory_id 或 scope, range, cursor)`：读取不可变修订、来源和替代/撤回关系。
4. `receipt(receipt_id 或 request_id)`：取得已持久提交点及对应结果。

`at` 的规范身份是 `commit_seq`，允许用已提交 receipt 解析它。若支持时间戳快捷方式，必须明确解析为不晚于该时间的已提交序号；原文 source timestamp 不参与这一解析。

MVP 的历史查询不得仅持有数据库运行期间的 snapshot。所有必要信息必须跨重启持久化。不能每修改一条记忆就复制整个数据库，也不能每次查询都从首条聊天开始 replay。spike 应选定有序 revision 索引、共享结构的检查点或其它可验证方案，并说明历史查询的读取范围和成本。

### 历史检索与当前检索必须明确区分

完整的历史 ANN 可以后置。MVP 的 `as_of` 状态、revision/history 和 receipt 不能后置。

历史管理接口接受 `at` 时，只能使用在该时刻有效的内容。主 Agent 的 consult 接口仍只有可选短 hint；历史范围与版本由外部 workflow 通过受控读取工具选择。MVP 可提供明确标记的 `historical_lexical` 检索或在限定历史状态上做有界的精确检索；超出可处理范围时返回需要缩小 scope/范围的错误。不能在当前 ANN 结果上加一个时间过滤，就把结果称为历史语义检索；这种方法可能永远找不到后来被替代的旧向量。

如历史语义模式尚未实现，应返回 `HISTORICAL_SEMANTIC_UNSUPPORTED`，同时让上述历史状态接口正常工作。结果均返回`read_seq`、`validated_at_seq`和实际`retrieval_mode`；RecallReceipt同样持久保存这些字段。需要完整结果的操作不得悄悄截断后返回成功。

`consult(hint?)` 的 hint 是简短、可省略的方向提示，上限 512 个 Unicode 字符；不另设必填 query/context/session 参数。hint 不改变权限、scope、authority 或撤回状态，不自动成为新记忆。worker 生成的检索 query 与管理查询的 at 属于内部能力，缓存键须包含实际影响结果的这些值。

## 7. 当前索引、失效与重建

### 权威提交和索引提交解耦

索引可异步建立，但任务必须随权威事务持久入队。只有模型结果通过 authority policy 的采用步骤后，才更新有效 head；embedding 完成不能自行把未采用候选升级为有效记忆。

组合 backend 不能假装 KV 与 LanceDB 有跨库事务：先提交权威数据和 outbox，再幂等应用检索变更，最后记录派生进度。Helix 也要明确其 strong/eventual search、pending overlay 和索引 activation 的实际边界，不能只根据“单引擎”省略验收。

每种索引及每个 generation 分别记录覆盖水位。水位表示已完整处理的提交前缀；乱序完成某个较新的任务不能跨过未处理缺口。无需索引或已经 superseded 的任务应有显式完成原因，使恢复可重现。

### 查询返回前的有效性检查

当前检索结果必须与权威 head/scope/生命周期匹配。即使向量或全文索引暂时包含旧条目，也不能把已撤回或已替代 revision 当作当前有效记忆返回。

在某个correction提交之后新开始的当前查询，必须读取不早于该提交的状态。更早开始的当前查询携带`read_seq`，最终返回前仍重查当前head、撤销及权限状态，并记录`validated_at_seq`。内部指定`min_commit_seq`时，不满足的旧结果必须等待、重算或明确失败。主Agent无需填写这些内部一致性参数。

**历史视图的例外必须明确：** 管理查询`at`固定的是当时已知且生效的语义状态；后来的替代/撤回不得把旧视图改写成当前状态。历史读取仍检查当前访问权限，权限撤销可以阻止读取，但不能伪造当年内容。历史结果标记`retrieval_mode`和历史`read_seq=at`，并记录当前权限复核点；不得把它冒充当前建议。当前consult返回作为有效建议的记忆须通过最新head校验，引用过去决策时则明确是历史证据。

索引落后时可以采用已实现的替代检索路径，也可以返回 `index_lag` / `resource_busy`。若返回部分候选，响应必须标明覆盖不足；“本次没找到”不能被表述为“该事实不存在”。

查询缓存至少绑定 scope、权威版本/失效 epoch、索引 generation、`at`、query/hint 和影响输出的策略版本。错误撤回要立即影响权威过滤与缓存有效性，不等待后台 ANN 删除完毕。

### Reindex 与模型切换

更换 embedding 模型、维度、距离函数或不可兼容 tokenizer 时，创建新 generation，在后台构建并验证。旧 generation 继续提供符合其覆盖语义的查询，直到新 generation 可以原子切换。查询向量只能送入相同模型/维度的 generation。

构建中途失败不影响权威记录；重新启动可以继续或安全重建。切换后旧 generation 的回收必须考虑进行中的读者和保留策略。MVP 不要求保留任意历史 ANN generation，也不能因此删除权威 revision。
