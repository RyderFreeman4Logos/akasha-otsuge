## 1. 原始证据先持久化

采集宿主实际提供的用户消息、显示给用户的回复、工具调用/结果以及必要的会话事件。先保存原文与来源，再异步提取、索引、摘要；模型服务不可用不能阻止采集。

RawEvent 至少记录 source\_adapter、source\_version、profile、runtime\_instance、session/thread/agent、branch、event\_id、parent/fork 关联、event\_time、observed\_time、content\_ref、content\_hash 和 visibility。记录当前可访问范围，不宣称恢复宿主从未保留的信息。

采集器必须处理增量片段、最终消息、文件截断或轮换、重复投递、恢复会话、压缩、fork 和迟到事件。幂等键基于来源身份与稳定事件标识，不能仅用正文 hash 去掉内容相同但真实发生两次的用户发言。

每次 compaction 保存其覆盖范围和原文引用。摘要可帮助导航，但不替代原文。主分支、已放弃分支和子 Agent 继承截止点都须可区分。

## 2. 记忆记录与来源

MemoryRevision 的逻辑字段：

```json
{
  "memory_id": "stable-logical-id",
  "revision_id": "immutable-revision-id",
  "kind": "decision | preference | fact | procedure | hypothesis",
  "scope": {"user": "...", "project": "...", "branch_or_version": "..."},
  "claim": "可独立理解但不脱离条件的内容",
  "rationale": "形成这个结论的原因",
  "conditions": ["何时适用"],
  "origin": "human_statement | reviewed_agent_proposal | extraction | auto_grill",
  "authority": "human_confirmed | delegated_approved | candidate",
  "source_spans": ["raw-event-and-range"],
  "approved_by": null,
  "valid_from": null,
  "valid_until": null,
  "supersedes": [],
  "generator": {"runner": "...", "model": "...", "prompt_version": "..."},
  "config_generation": "...",
  "commit_id": "..."
}
```

字段与枚举可在领域设计 Issue 中归并，但必须保留上述语义。时间有效性、录入时间和修订提交时间不能混成一个 timestamp。

## 3. 权威与适用范围

- 人的明确决定及其对Agent建议的审阅/修改，必须连接到可信调用方的原始用户消息或真实review操作。用户可一次配置采纳策略：明确决定可自动形成有来源的决定事件，无需每条再点一次确认；仅有原始消息的user标签、worker转述或模型高置信度不足以伪造`human_confirmed`。
- 用户只说“也许”“可以考虑”时，不可仅因为提取模型高置信度就标成已确认长期原则。
- 代理经授权自动批准可以成为当前有效工作依据，但来源仍是 delegated\_approved。它不能变成人类亲自确认。
- 当前明确指令、项目范围、版本条件、后续替代关系共同决定适用性；不能用一个全局数值权重覆盖所有情境。
- 原始材料里的网页指令、仓库文字、模型猜测不自动取得用户权限。
- 用户 taste 是可版本化的规范性偏好。技术测试可以证明某事实错误，但不能单独证明人的偏好改变。

默认检索优先检查当前适用的有效决定；候选和冲突内容可作为有明确来源的补充。自动策略不应被实现成“没有逐条人工 review 就什么都不能用”。

## 4. 提取、向量与重排

MVP 支持独立配置 text/extractor、embedding、reranker 与 researcher。所有本地模型调用遵守 1700 秒 timeout 规格。不要硬编码当前用户的私人 endpoint、模型 ID 或凭证。

基础路径必须在未配置 embedding/reranker 时使用关键词/结构化条件与所选 CLI 调研完成。配置向量模型后启用混合检索；重排器是可配置步骤，不是隐含付费依赖。

提取以足以理解决定的问答/工具证据单元进行，避免把条件切掉。只处理新增或明确需要重提取的内容；模型失败保留任务与原文，不丢弃。

派生记录保存 model\_id、模型版本或指纹、维度、规范化策略和索引 generation。更换 embedding 模型或维度需要新 generation，不能把旧向量和新查询向量直接混用。

MVP 必须有 schema 校验、来源可解析检查、重复候选合并、冲突候选保留及可重建索引。语义合并必须保留原始多个来源，不能伪造它们来自同一次谈话。

## 5. Auto-Grill 最小实现

目标是在用户不参与每一步时继续探索需求与设计问题，并产生可审阅的候选决定。

1. 从当前问题、已有决定和未决点选取有限的问题集合。
2. 一个 runner 提出问题和方案；同一 runner 的隔离角色或另一个 runner 进行质疑、证据核对和替代方案分析。
3. 在共享预算与有限轮次内修改方案，保留真实分歧。
4. 输出决策候选、理由、最强反方、适用条件、未决问题和来源。
5. 按 review 策略激活或排入 review；不得因为多个模型一致就标成用户确认。

必须支持只配置一个 CLI 的模式，以及两个不同 CLI 的组合模式。不是必须有两家模型，也不宣称同一模型的多个角色具有统计独立性。

默认轮次、模型、思考配置、费用和时间预算应可配置并热重载到新任务。遇到没有新证据、预算到达、问题已解决或用户要求停止时结束；不无限互相质疑。

## 6. 人工与自动 Review

至少提供三种策略：

- manual：候选进入 inbox，由用户批准、修改或拒绝。
- selective：按来源、范围、影响和冲突情况决定自动接受或人工处理。
- automatic：在用户给出的 taste、访问权限及修订范围内自动运行；低证据或高影响问题保留可见调查条目。

人工 review 不只存 approve/reject，也保存修改内容和理由。批量 review 可以存在，但每条修订都保留其批准依据。

用户在普通工作会话里纠正 Agent 时，采集器登记 CorrectionEvent；后台调查读取相关 receipt、原文和改动。当前工作不必等待整套记忆调查完成。明确错误可先暂停相关记忆的检索曝光，随后按策略修复。

## 7. 必须验收的反例

- 模型把“这次先用 A”提取成“所有项目永远用 A”：不得静默扩大 scope。
- Auto-Grill 形成一致意见：不能标为 human\_confirmed。
- 用户审阅时修改方案：最终版本必须指向修改后的决定，并保留旧提案。
- 第三次压缩后查询第一次压缩前的明确约束：必须能回到原文。
- 同一句话在两个时刻分别发生：不能错误去重为一次。
- 模型服务断开：采集继续，提取队列可恢复。
- 用户配置仅一个 CLI 且无付费 API：基本采集、调研、提取和 Auto-Grill 可以完成。
