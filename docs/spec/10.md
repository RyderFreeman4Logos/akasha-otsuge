所属规格：[跨 Agent 记忆系统｜MVP 开发规格与 Issue 计划](https://app.notion.com/p/40117b41f58c81acb9f3e88ffe51e135)

**本页是交给开发 Agent 的一次性项目执行说明。** 当前工作是规格准备；新仓库、GitHub Issues 和产品实现均由后续开发任务创建。本文的 MVP 编号是稳定计划 ID，不等同于 GitHub 自动分配的 Issue number。

## 1. 可直接交给开发 Agent 的任务

> 先阅读本规格首页、产品契约、本执行手册、Issue索引和验收矩阵，保存全量规格快照。按照最新规格建立一个不同于mempal的新名称仓库，先创建完整GitHub Issue集合和依赖映射，再按依赖顺序一次完成一个Issue，直到所有必需验收通过并交付可安装的MVP。保留需求、来源、实际测试和实现之间的对应关系。遇到真实阻塞要如实记录；不通过删需求、空实现、仅mock或改成“未来工作”来宣布完成。

先理解产品契约和完成条件；实施每个Issue前，再读取它的完整正文及关联技术章节，核对接口、配置、存储、权威与纠正语义。源代码、旧聊天、旧README中的建议不覆盖本规格已明确的决定。

**开发上下文管理：** 全量快照用于精确引用、搜索和创建完整Issues，不要求一次把41页装入同一模型上下文。创建Issues时逐页精确导出正文，避免模型重述丢掉验收项；实现时围绕当前Issue渐进读取。每完成一项，记录当前commit、已通过证据、下一项依赖及未决问题，压缩或重启后据此恢复；重要决定仍保留原始规格链接。

## 2. 创建仓库之前的准备

1. 记录本规格版本、读取时间和全部页面URL；导出一份可阅读的规格快照到新仓库的 `docs/spec/`，保留外部依据链接。不要只提交会随时变化的Notion链接。
2. 确认实际可用的GitHub身份与目标owner；选择未占用、不同于mempal的项目名。本文 `mem` 是临时命令名，初始化时统一替换并记录，不把名称选择扩展成长时间命名工作。
3. 默认创建**私有仓库**，除非用户已指定公开；不覆盖任何已有仓库。遵守实际平台权限及用户已给出的发布要求。
4. 为开启Issues和默认分支可做最小README/许可证/规格快照提交；**除这种必要初始化外，在完整Issue集合创建完成前不开始产品实现。**
5. 读取源项目许可证并在复制任何代码前记录来源及保留义务；迁移不等于复制整个目录或全部依赖。

## 3. 必须先建立完整 Issue 集合

创建MVP-001～MVP-028共28个真实GitHub Issues，标题统一为 `[MVP-001] 建立 Rust/Linux 项目骨架与可执行开发门槛` 这类格式。每个Issue以对应Notion子页为正文依据，必须保留目标、范围、非目标、需求ID、依赖、验收及完成证据；复制时将Notion原生引用转成可点击的普通链接。

采用两遍操作：

1. 第一遍创建全部Issues，保存每项的真实number和URL；失败时查询已创建条目再继续，避免重复创建。
2. 第二遍回填依赖的真实Issue链接、规格来源、对应验收页及milestone。可使用平台原生依赖；平台不支持时，在正文维护 `Blocked by` 链接列表。
3. 在 `docs/plan/issues-index.md` 或等价机器可读清单中保存 `MVP ID → GitHub number/URL → deps → REQ IDs`；这是映射，不是假定GitHub从#1开始。
4. 建立 `MVP` milestone；标签保持少量且实用，如 `mvp`、`blocked` 和必要领域标签。不要为规划本身创建大量流程。
5. 运行清单检查：28个计划ID唯一、链接有效、所有依赖存在且无环、24项需求均被实质实现Issue覆盖。MVP-028的全量终验不能代替其它Issue的需求覆盖。

**进入MVP-001前的门槛：全部28个真实Issues已存在、依赖已回填、映射已落盘。** GitHub暂不可用时可准备精确Issue正文和清单，但不得把本地草稿标记为“GitHub Issues已创建”。

## 4. 默认实施顺序

数字顺序MVP-001→MVP-028已经是一个有效拓扑顺序，默认直接采用。一次只有一个实现中的主Issue；可以并行进行该Issue内部的研究、代码审查或独立测试，但不要同时推进多个未完成的功能Issue。

每个Issue使用以下过程：

1. 阅读本Issue及依赖的完成证据，核对相关规格；记录本次要改变的行为和最小实现边界。
2. 检查实际工具、库和宿主的稳定版本与能力，固定依赖和测试环境。文档示例不等于本机已支持。
3. 以当前默认分支为基础实现最小完整切片；可采用独立分支/PR，避免无关重构。模块数量随真实边界增长，不先搭一套空插件框架。
4. 运行本Issue必要测试。持久化、并发、版本和长超时需要真实有意义的验证；低影响文档或可逆改动不机械增加测试。
5. 核对验收条件，附实际命令、环境、结果、相关日志/产物与commit；将失败、未执行和通过明确区分。
6. 完成代码审查并按仓库规则合并。只有依赖条件、验收与证据均满足，才关闭Issue；不能先关闭再承诺后补测试。
7. 更新映射与需求覆盖，继续下一项。测试只因具体风险或门槛需要而重复，不把同一昂贵长测在所有Issue中机械重跑。

真实外部阻塞可以把当前Issue标为blocked，再选择已满足依赖的下一项，但必须写明原因、缺少的条件及恢复动作；这不是删除依赖或默认允许并行实现。最终必需Issue不得带阻塞结案。

## 5. 必须在前期解决的设计门槛

- MVP-003必须做真实存储实验，锁定**一个**生产backend。先评估Helix embedded；只有未满足硬条件才评估规定的备选。两个都不满足时形成具体阻塞报告，不悄悄换回SQLite或无限扩展候选清单。
- MVP-002先验证配置管理模块，daemon和通知消费者分别在后续Issue集成；不能让前期Issue等待尚未实现的后期模块。
- MVP-011先冻结参考集、oracle与评价规则，MVP-016实现prompt前校验其commit/hash，MVP-027使用该集合做最终评测；不能完成调参后再选择验收样例。
- 采集必须有真实会话/子Agent/分支身份，禁止用cwd猜身份。某宿主缺乏必要信息时先做能力验证，不能拿错误绑定当暂时可用。
- 默认worker并发较低时，父任务不能占满执行槽再等待孙子任务；资源不足要直接给出可处理的委派不可用状态，允许当前worker自行完成。
- 单一已登录CLI必须支撑基础采集、consult、提取和Auto-Grill；没有独立embedding/reranker/text endpoint仍可工作。配置了这些服务后，它们必须真实参与功能。
- 外部记忆修订走有版本和scope约束的patch；索引与内容都有真实实现，不能把接口存在当能力交付。

## 6. 外部依赖和权限不足时怎么处理

四种CLI的真实认证、适合的Linux测试机器及大规模数据实验环境属于实际验收条件。不要伪造账号、结果或未运行的基准。如果缺少某项，先完成已授权且不依赖它的工作，明确记录最小所需条件；真实连接、长测或规模门槛仍未通过时，MVP状态必须保留未完成。

已有用户授权足以覆盖的普通初始化、修复和可逆步骤无需反复确认。平台强制审批、破坏性操作或新的外部发布范围按实际权限处理；不得修改安全规则绕过阻塞。

## 7. 规格变化与新发现

新发现通过简短ADR或规格变更记录处理：问题、证据、考虑的替代、决定、受影响需求/Issue/测试。区分“换实现方式”和“减少用户需求”。在满足原契约前提下，开发Agent可以自主选择具体库、内部结构和实现细节；减少四工具、删历史、降低长超时、跳过压力验收等属于范围变化，不能自行宣布完成。

发现必需缺陷时可以拆子Issue或新增Issue；保留原MVP ID、依赖和验收责任，并将新增阻塞接入MVP-028。既不强求永远只有28个Issue，也不允许用拆分丢掉工作。

## 8. 最终交付

最终必须提供：可安装Linux发行包、不可变commit/tag、完整使用/恢复文档、源与数据迁移报告、真实四工具集成记录、近1700秒真实长测、50GB/100客户端资源报告、质量报告和逐条需求覆盖矩阵。

先以发行候选包完成验收，再根据授权与仓库规则发布。最终状态报告区分已通过、已知边界和仍未完成的事项。只要还有必需验收缺失，就不能写“MVP完成”。
