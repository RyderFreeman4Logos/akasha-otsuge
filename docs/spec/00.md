本规格用于指导一个新的 Rust 记忆项目：从 mempal 有选择地迁移能力与数据，以更少的耦合实现跨 Agent 的记忆调研、可追溯决策和可纠正历史。

**交付状态：规格与实施计划；尚未创建新 GitHub 仓库、GitHub Issues 或实现代码。** 开发Agent先阅读本页、产品契约、执行手册、Issue索引与验收矩阵，保存全量规格快照；再创建新仓库和完整Issue集合，随后按依赖顺序逐项实施，并读取当前Issue的关联技术章节。Notion 中的 MVP 编号是计划编号，不是假定的 GitHub Issue 号码。

规格版本：**v0.1**。基线日期：2026-10-22。

## 本轮已确定的调整

- 求助入口支持一个**可选、简短的意图提示**。例如 `mem consult "核对这次数据库选择的历史约束"`；也允许 `mem consult`。调用方不需要生成上下文摘要、会话 ID、历史引用或代码包。
- 当前调用身份、分支、历史位置和代码现场由适配器在程序侧取得；外部调研 Agent/workflow 渐进读取必要信息，可继续委派子任务。
- **本地模型默认 timeout 为 1700 秒。** 外层 workflow、runner、HTTP 读取和无输出检测不得无意间缩短这个默认值；队列等待与执行时间分别管理。
- 配置尽可能热重载：完整验证后原子切换，运行任务固定配置版本，不能部分应用一份无效配置。必须重启的少数项应明确列出。
- Claude Code、Codex、Hermes Agent、pi 均须支持单独使用，也可任意组合调用方与调研执行器。不能要求同时安装 Claude 和 Codex。
- 核心使用 Rust，默认 CLI + 本地 daemon + 私有 IPC；MVP 不依赖 MCP、HTTP 监听端口、网页 UI 或云控制面。
- 不默认采用 SQLite。HelixDB embedded 是先验证的候选，最终选择由明确的存储实验决定；MVP 只交付一种正式后端。
- 保留原始证据、记忆修订、实际返回记录和纠正依据。支持人工 review、选择性 review 与按用户策略自动运行。

## 产品应完成的工作

用户在任一支持的 Agent 中工作，必要时给一句方向或直接求助。系统自动定位调用现场，查找当前和多次压缩之前的相关原文、项目代码、有效记忆及用户决策，只返回对当前工作有帮助的结果。

对话和工具记录在后台持续保存；提取与 Auto-Grill 生成有来源的候选记忆。人的明确决策、taste 和对候选内容的审阅结果有可验证的来源，模型不能伪造“用户确认”。在用户纠正或软件运行暴露问题后，外部 Agent 可以调查并提交版本化修订。高优先级 review 可通过用户配置的通知插件推送。

## 阅读与执行顺序

1. 产品契约与 MVP 边界：理解必须交付什么，以及明确不做什么。
2. 架构、调用接口、配置与存储：理解模块契约及运行语义。
3. 记忆生成、纠正与通知：理解信息如何进入、生效、被替代。
4. 验收矩阵：理解何时可以说 MVP 已完成。
5. 开发 Agent 执行手册与 Issue 清单：先建全部 Issues，再按依赖逐个处理。
6. 研究依据与决策记录：区分已核查事实、待验证选型和项目自身要求。

各子页面是本规格的组成部分。技术文档中的命令、JSON 和配置片段是**拟议接口**，由开发 Agent 实现；它们不表示产品已经存在。

## 完成的定义

只有所有必需 Issue 的验收条件均有可复现证据、所有必需需求均有对应实现、四种宿主真实接入通过，并且安装、资源限制、恢复及整体验收完成，才可以声明 MVP 完成。接口占位、仅 mock 通过、将必需功能改成“后续支持”，都不能计为完成。

允许拆分 Issue 或修正实现策略；必须保留需求覆盖和依赖，不能通过关闭、合并或改名丢失原有验收责任。库版本与宿主能力以实际实施时的 latest stable 和记录的固定版本为准。

## 项目命名与迁移原则

新仓库使用不同于 `mempal` 的名称。本文的 `mem` 是 CLI 占位名；开发 Agent 在初始化时选择可用名称并记录。迁移对象是经验证需要的能力、可复用的小段代码和可导入数据，不要求复制旧仓库目录结构或完整功能集合。

旧讨论中“强制零参数”“固定 Claude + Codex”“默认 SQLite”“MCP 作为核心入口”“45 秒调研 deadline”等建议，均不构成本规格要求。与本轮明确决定冲突时，以本规格的需求和变更记录为准。
