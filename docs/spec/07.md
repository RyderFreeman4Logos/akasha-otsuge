## 1. 事件与因果证据

OutcomeSource 接收结构化测试结果、编译/运行故障、用户纠正和可配置的程序使用反馈。每个事件有 event\_id、发生时间、来源、severity、执行/构建关联和 evidence\_ref。

必须建立可追踪关系：memory\_revision → recall\_receipt → agent\_run → worktree/build artifact → outcome。关联尽量由运行时自动记录，不增加主 Agent 的记忆使用报告负担。

receipt 证明“被返回/可能暴露”，不是“确实使用”，更不是“确定造成失败”。调查应区分错误记忆、过期条件、检索遗漏、Agent 执行错误、无关代码问题、环境故障与需求改变。命令非零退出也不自动等于故障，例如正常的无匹配搜索。

无法取得构建或实际使用关联时，可以创建人工可见的可疑条目，但不能伪造因果链。

## 2. 外部调查与修订

调查 Agent 与存储内核分离，使用配置的 AgentRunner 执行。它读取证据、必要上下文与相关代码，形成报告或补丁；数据库本身不凭内部模型猜测自行改写人的意图。

拟议 Patch：

```json
{
  "patch_id": "idempotent-id",
  "expected_heads": [{"memory_id": "...", "revision_id": "..."}],
  "changes": [{"operation": "replace | supersede | suspend | restore", "memory_id": "...", "new_revision": {}}],
  "reason": "为什么需要这项改动",
  "evidence_refs": ["..."],
  "origin_outcomes": ["..."],
  "editor_run_id": "...",
  "config_generation": "..."
}
```

提交必须在短事务中检查 expected\_heads、当前写权限和必要证据，新增修订、更新 head、登记派生索引任务及相应 review/outbox 事件。调查和模型调用不能占着写事务等待。

外部 Agent 可以使用 CLI 导出可编辑文档、生成 patch 并提交；人也能用同一机制编辑。不要要求外部 editor 直接操作底层数据库或修改原始事件文件。

修订冲突返回可解析的 REVISION\_CONFLICT；禁止 last-write-wins 覆盖他人的纠正。回滚是一项新修订，保留被回滚历史和无关的后续修改。

## 3. 自动化策略

- 明确用户纠正并且能定位对象：创建高优先级调查，必要时立即暂停该记忆的正常曝光。
- 可复现的代码/依赖事实冲突：策略允许时可自动修订，并保存复现证据。
- 证据不足、范围不明或可能改变人的 taste：标为可疑并排入 review；不将不确定性伪装为事实。
- 配置可以允许自动修技术事实，也可以要求全部 review。执行器强弱和自动程度独立设置。
- 已被修订的记忆若仍在待返回结果中，最终返回前必须重新检查有效性。

## 4. 三组状态分别管理

记忆状态：active、suspended、superseded、retired。

调查状态：open、investigating、resolved、dismissed。

投递状态：pending、sending、sent、retrying、failed。

通知已读或被确认不等于调查已解决，更不等于补丁已批准。调查被排除，也不必生成一个虚假的记忆修订。

review 优先级可结合影响范围、证据强度、复发次数和未来曝光可能性。先采用可解释的规则，不需要第一版训练风险模型。相同根因合并为同一 review，保留重复事件数量与引用。

## 5. Notifier 契约

Notifier 的职责是投递和更新内容，不负责判断记忆是否错误。MVP 使用统一接口，具体渠道由配置或插件提供。

```json
{
  "notification_id": "...",
  "idempotency_key": "review-id:event-generation:route",
  "review_id": "...",
  "priority": "normal | high | urgent",
  "summary": "...",
  "evidence_locator": "...",
  "action": "create | update",
  "external_message_id": null
}
```

应支持 send；update、ack callback、富文本等以 capability 声明。插件不能支持 update 时允许发送去重摘要，不假设所有提供方都有同一功能。

创建 review 与写入 outbox 需要同一事务。worker 持久重试、退避、记录外部消息 ID；跨进程/渠道采用至少一次投递加幂等设计，不宣称普遍的严格 exactly-once。

通知默认发送简短问题、优先级和查看入口，不复制完整聊天或代码。路由、quiet hours、digest、优先级阈值、插件命令和插件配置应尽量热更新。

本地 review inbox 必须可通过 CLI 实际使用。至少提供一个 stdio 插件示例，用文件/终端演示真实发送、失败重试和去重；邮件、Slack、Lark 等专用 SDK 不属于 MVP 必需项。

## 6. 热重载与通知交互

尚未投递的任务在领取时按当前 route policy 解析，记录 route/config generation。已成功投递的任务不会因为配置改变而自动重发。进行中的投递保留自己的幂等键与已选择的提供方，避免重载导致双发。

关闭通知不删除 review 或 outbox 历史。权限撤销、秘密轮换或插件取消应明确影响正在进行的投递，不能继续使用已经撤销的能力。

## 7. 验收

- 同一失败由 100 个执行来源重复报告时，产生一个可更新 review，并保留影响计数。
- 仅发生环境断网时，不自动修改用户 taste 或无关技术记忆。
- 两个 editor 同时基于旧版本提交时，不静默丢失其中一个修改。
- daemon 在写入 review 后、发送前崩溃，恢复后仍可投递。
- 已发送但未记录成功时崩溃，依靠幂等键/渠道能力尽量避免重复，并保留可审计状态。
- Notifier 插件失败不会阻止采集、查询和记忆修订。
- 自动修订后，当前搜索不再返回被撤回版本；历史状态和旧 receipt 仍可查看。
- 人类仅在出现问题时纠正一次，系统能够独立完成调查、修订或生成明确 review 条目。
